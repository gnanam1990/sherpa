## Notable departure from the kickoff prompt

The kickoff said use viem `getEnsAddress` for Basenames. Research showed
Base mainnet doesn't deploy an ENS Universal Resolver — `getEnsAddress`
would fail. Surfaced the conflict before coding; user selected "direct
L2Resolver read via viem.readContract." Hardcoded the L2Resolver address
in `@sherpa/config.ONCHAIN_ADDRESSES` with a source comment.

The kickoff also said "multicall (getCode + getTransactionCount)." Real
Multicall3 only batches contract reads, not RPC methods like
`eth_getTransactionCount`. Implemented as `Promise.all` for parallel
reads — same wall-clock without the wrapper.

## apps/api wiring (in this PR)

`apps/api/src/server.ts` now constructs a real resolver via
`defaultResolver(config)` and passes it through to `/api/balance/:addr`.
`buildServer` accepts an injected `resolver` for tests. The Vercel KV
layer engages only when both `KV_REST_API_URL` and `KV_REST_API_TOKEN`
are present in config; otherwise the LRU is the only cache. `@vercel/kv`
moved from `@sherpa/identity` to `apps/api` (a dangling dep on a package
that didn't import it).

A new apps/api test injects a stub resolver and verifies a `.base.eth`
input round-trips through the new path (was returning
`api_error: backend not configured` before).
