# Devlog: Stage 6 P2 — Notification System

**Date:** 2026-05-15
**Stage:** 6 P2
**Author:** Sherpa

## What shipped

### Parser (core)
- `NOTIFICATION` intent with deterministic parsing for:
  - `notify me when <condition> via <channel>` → `notificationAction: 'subscribe'`
  - `set my notification channel to <channel>` → `notificationAction: 'set_channel'`
  - `show my notifications` → `notificationAction: 'list'`
- Regex patterns in `parser.ts:109-112`
- Slots: `notificationAction`, `notificationCondition`, `notificationChannel`
- Supported channels: `push`, `email`, `farcaster`, `telegram`

### Notification tools
- `dispatchNotification(channel, recipient, payload, deps)` — unified dispatcher
- Channel stubs: `sendPushNotification`, `sendEmailNotification`, `sendFarcasterNotification`, `sendTelegramNotification`
- Types: `NotificationPayload`, `NotificationResult`, `ChannelConfig`, `NotificationDeps`

### Tests
- `packages/core/src/index.test.ts` — 4 NOTIFICATION parser tests
- `packages/tools/src/notifications/dispatcher.test.ts` — 3 dispatcher tests (push, email, unsupported channel)

### Documentation
- Decision record: `docs/sherpa/decisions/2026-05-15-notifications-stage-6.md`

## Integration notes
- Channel implementations are stubs — return success with placeholder IDs
- `dispatchNotification` gracefully rejects unsupported channels with `{ success: false }`
- No new transaction surface — notifications are read/write config only
- Parser patterns match before ALERT (subscribe regex is more specific)
